# ADR 0005 — RON for authored data, MessagePack for saves

**Status:** Accepted
**Date:** 2026-07-27
**Decision maker:** John D. Pope

## Context

The engine has three distinct data needs:

1. **Authored data** — scenes, dialog trees, items, manifest. Written by designers, edited in text editors, hot-reloaded via file-watch.
2. **Save data** — player save slots. Binary, compact, versioned.
3. **Fixture data** — test assets, dev-mode placeholders.

Format options:
- **RON** (Rust Object Notation) — readable, supports comments + trailing commas
- **JSON** — ubiquitous, no comments, no trailing commas
- **YAML** — readable, whitespace-significant, surprising behavior at scale
- **TOML** — great for config, bad for nested structures
- **MessagePack** — binary, compact, schema-flexible
- **bincode** — binary, compact, Rust-specific

## Decision

- **Authored data → RON.** All `*.scene.ron`, `*.dialog.ron`, `*.item.ron`, `manifest.toml` (TOML for the manifest, RON for content).
- **Save data → MessagePack** via `rmp-serde`. Binary, ~10× smaller than JSON.
- **Fixture data → JSON.** Existing `scene-engine` fixtures (`ardy_walk_demo.json`) are JSON; we don't migrate them. New fixtures are RON.

## Rationale

### Why RON for authored data

1. **Comments.** Designers can document a hotspot:
   ```ron
   Hotspot((
       id: "hotspot_door",
       // North-east door to the cottage. Player must have key_cellar to enter.
       polygon: [(0.4, 0.6), /* ... */],
       on_click: Action("enter_cottage"),
   ))
   ```
   JSON doesn't allow comments. Designers end up with `_comment` fields.
2. **Trailing commas.** Adding a new field at the end of a list doesn't require touching the previous line:
   ```ron
   nodes: [
       Node(( /* ... */ )),
       Node(( /* ... */ )),  // <- add new node here, no need to add comma to previous
   ]
   ```
   JSON's strict-no-trailing-comma rule makes diffs noisy.
3. **Typed round-trip with serde.** `#[derive(Deserialize)] struct Scene` parses RON cleanly with the `ron` crate. No JSON Schema intermediate.
4. **Diff-friendly.** Pull requests read like diffs, not reformatted JSON blobs.
5. **Familiar shape.** Looks like Rust syntax. Designers who've seen any C-family language can read it.

### Why MessagePack for saves

1. **Compact.** ~10× smaller than JSON for the same data. A 50KB JSON save is ~5KB MessagePack.
2. **Binary.** Players can't easily hand-edit saves (which is a feature — protects integrity).
3. **Schema-flexible.** Migration is easy: decode to `serde_json::Value` intermediate, patch, re-encode to current struct.
4. **Fast.** `rmp-serde` is faster than `serde_json` for both encode and decode.

### Why JSON for fixtures

1. **Existing scene-engine fixtures are JSON.** `ardy_walk_demo.json` is consumed by `crates/locomotion/` tests. Migrating to RON would break those tests for no benefit.
2. **Cross-language.** Fixtures are sometimes generated by external tools (e.g., a Python script that bakes sprite atlases). JSON is universal.
3. **Test-only.** Fixtures don't ship in the binary; they're only loaded by tests. Readability matters less than round-trip stability.

## Consequences

- **Positive:** Authored data is designer-friendly and VCS-friendly. Saves are small and tamper-resistant. Fixtures interop with existing tooling.
- **Negative:** Three formats instead of one. Engineers must remember which to use where. (Mitigated by clear rules in `docs/DATA-FORMATS.md`.)
- **Negative:** RON is less known than JSON. Designers may need 30 minutes of orientation. (Worth it for the long-term readability gain.)
- **Neutral:** `ron`, `serde_json`, `rmp-serde` are all `serde`-compatible. Same Rust structs serialize to all three.

## When to revisit

- If we ever need to support user-authored mods (not currently planned), evaluate Lua-tables or JSON for mod data.
- If saves grow large (>1MB), evaluate `zstd` compression on top of MessagePack.

## Alternatives considered

**YAML**: Rejected for whitespace-significance (large diffs become painful), surprising behavior (Norway problem, implicit typing), and historical security issues (Python YAML `safe_load`).

**TOML for everything**: Rejected — TOML's flat key-value shape is poor for deeply-nested data like dialog trees.

**JSON for everything**: Rejected — no comments, no trailing commas, larger saves.

**bincode for saves**: Rejected in favor of MessagePack. bincode is slightly faster but doesn't have a `Value` intermediate, making migrations harder.
